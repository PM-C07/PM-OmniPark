- **Oggetto:** le funzioni di accesso di `src/persistence/accessoDati/walletSoste.ts`. `addebita` è già verificata in `cp_persistenza_base.md` (TF-BASE-37…44).
- **Fonti dell'esito atteso:** sequence diagram e casi d'uso indicati per ogni funzione (inventario del piano approvato); vincoli dello schema; `docs/rad/requisiti.md`; `docs/rad/vincoli_dominio.md` §2; statechart `SCD_2` e `sincronizzazione_eventi.md`; codici di errore di `docs/test/cp_persistenza_base.md`.
- **File di test:** `src/persistence/accessoDati/walletSoste.db.test.ts` (eseguito da `npm run test:db`).

## 1. Tracciabilità

Ogni frame riporta un solo riferimento, scelto in quest'ordine: un requisito dell'Elenco (`RF_…`, `NRF_…`) se il suo testo copre davvero il comportamento; altrimenti il vincolo di dominio `VD_<n>` (`docs/rad/vincoli_dominio.md` §2); altrimenti `SCHEMA` se il frame verifica un vincolo specifico dello schema; altrimenti `ISSUE_9`, `ISSUE_10` o `ISSUE_33` per le scelte delle issue #9, #10 e #33 e dei piani approvati di OMP-45, OMP-46 e OMP-61.

Nome del test: `<riferimento> · <frame> · <descrizione> → <esito>`, per esempio `RF_WALLET_3 · TF-WS-08 · cronologia del wallet 2 → 6 movimenti dal più recente`.

## 2. Funzioni verificate (firme)

Il primo parametro è sempre l'esecutore (`Esecutore = Pool | PoolClient`, da `./esecutore`); nei test è il client della transazione del test. Gli id e gli importi (centesimi) sono `number`; gli istanti `Date`. Gli errori sono `ErroreDominio` con il `codice` indicato (`./errori`).

```ts
type StatoSosta = "ATTIVA" | "SCADUTA" | "TERMINATA";
type Pagamento = "PAGATA" | "GRATUITA";
type Sosta = {
  id; automobilistaId; veicoloId; targa: string; stalloId; stato: StatoSosta;
  orarioDiAvvio: Date; orarioDiScadenza: Date; pagamento: Pagamento;
  dichiarazioneDiPermesso: string | null; fotoDelPermesso: Buffer | null;
};
type MovimentoDelWallet = { id; walletVirtualeId; tipoDiMovimento: "RICARICA" | "ADDEBITO"; importo; dataEOra: Date; sostaId: number | null };

creaWallet(es, automobilistaId: number): Promise<number>;                         // id del wallet
trovaWalletDiAutomobilista(es, automobilistaId: number): Promise<{ id: number; saldo: number } | null>;
registraRicarica(es, dati: { walletVirtualeId; importo; dataEOra }): Promise<MovimentoDelWallet>;
movimenti(es, walletVirtualeId: number, limite?: number): Promise<(MovimentoDelWallet & { targa: string | null; numeroStallo: number | null; area: string | null })[]>;
// dal più recente (data_e_ora decrescente, poi id decrescente); targa della sosta per gli addebiti, null per le ricariche.
// OMP-65: numero dello stallo della sosta e nome della sua area (null per le ricariche); `limite` facoltativo, senza
// limite tutti i movimenti. I nuovi campi e il limite sono verificati attraverso il Wallet (cp_movimenti.md);
// TF-WS-10…12 sono invariati
creaSosta(es, dati: { automobilistaId; veicoloId; stalloId; orarioDiAvvio; orarioDiScadenza; pagamento;
  dichiarazioneDiPermesso?: string; fotoDelPermesso?: Buffer }): Promise<number>; // la sosta nasce ATTIVA
trovaSosta(es, id: number): Promise<Sosta | null>;
trovaSostaPerAggiornamento(client: PoolClient, id: number): Promise<Sosta | null>; // OMP-61: come trovaSosta, con la riga bloccata (FOR UPDATE) fino alla fine della transazione
trovaSostaConStalloPerAggiornamento(client: PoolClient, id: number): Promise<SostaConStallo | null>; // OMP-63: come trovaSostaPerAggiornamento, con tipoDiStallo ed enteId dell'area dello stallo
sostaAttivaPerVeicolo(es, veicoloId: number): Promise<Sosta | null>;
sostaAttivaSuStallo(es, stalloId: number): Promise<Sosta | null>;
sostaPerTargaSuStallo(es, targa: string, stalloId: number): Promise<Sosta | null>; // la più recente per orario di avvio, in qualsiasi stato
sosteAttiveDiAutomobilista(es, automobilistaId: number): Promise<Sosta[]>;        // ordinate per orario di avvio, poi id
aggiornaScadenza(es, sostaId: number, nuovaScadenza: Date): Promise<boolean>;     // solo se ATTIVA; false altrimenti
sosteDaScadere(es, istante: Date): Promise<number[]>;                             // id delle ATTIVA con scadenza ≤ istante, ordinati
impostaSostaScaduta(es, sostaId: number): Promise<boolean>;                       // ATTIVA → SCADUTA senza condizione sull'orario; false altrimenti. Dalla OMP-61 solo per preparare i dati nei test
impostaSostaScadutaSeRaggiunta(es, sostaId: number, istante: Date): Promise<boolean>;
// OMP-61: ATTIVA → SCADUTA solo se l'orario di scadenza è ≤ istante; false altrimenti. Usata dall'allineamento temporale
terminaSosteScaduteDelloStallo(es, stalloId: number): Promise<number>;
// SCADUTA → TERMINATA per tutte le soste scadute dello stallo, con dichiarazione e foto eliminate; restituisce quante
sostaInCorsoSuStallo(es, stalloId: number): Promise<Sosta | null>;                // OMP-45: la ATTIVA, altrimenti la SCADUTA con scadenza più recente
sosteInCorsoDiAutomobilista(es, automobilistaId: number): Promise<Sosta[]>;       // OMP-45: ATTIVA e SCADUTA, dalla più recente
sosteInCorsoDiTarga(es, targa: string): Promise<Sosta[]>;                         // OMP-46: ATTIVA e SCADUTA del veicolo con la targa, dalla più recente
```

Ordinamento degli elenchi (sempre con l'id come ultimo criterio di spareggio): `movimenti` per `data_e_ora` decrescente, poi id decrescente; `sosteAttiveDiAutomobilista` per `orario_di_avvio` crescente, poi id crescente; `sosteDaScadere` per `orario_di_scadenza` crescente, poi id crescente. `sostaPerTargaSuStallo` sceglie la sosta con `orario_di_avvio` più recente e, a parità, l'id maggiore. `sostaInCorsoSuStallo` considera solo le soste `ATTIVA` e `SCADUTA` e sceglie prima la `ATTIVA`, poi la `orario_di_scadenza` più recente, poi l'id maggiore; `sosteInCorsoDiAutomobilista` restituisce le soste `ATTIVA` e `SCADUTA` per `orario_di_avvio` decrescente, poi id decrescente; `sosteInCorsoDiTarga` fa lo stesso per le soste del veicolo con la targa indicata, su qualsiasi stallo.

## 3. Ambiente

- Database di test riportato allo stato noto da `preparaDatabaseDiTest()` nel `beforeAll`; ogni test in una transazione annullata (`iniziaTransazioneDiTest()` / `annullaTransazioneDiTest()`), con il client come esecutore.
- Istante di prova `I` = `2026-11-20 09:00:00+01`; `I+1h` = `2026-11-20 10:00:00+01`. Permesso «completo»: dichiarazione `Dichiaro di esporre il permesso previsto per lo stallo` e foto di 1024 byte (`Buffer.alloc(1024, 0xff)`).
- Le soste preesistenti richieste dai frame si inseriscono con SQL nella transazione del test (colonne sotto), salvo dove il frame nomina `creaSosta`; se il frame non indica gli orari, valgono `I` → `I+1h` (anche per le soste `SCADUTA` di TF-WS-42).
- Un automobilista senza wallet si prepara con SQL: `INSERT INTO utente (email, hash_password, ruolo) VALUES ('senza.wallet@omnipark.example', 'hash-di-prova', 'AUTOMOBILISTA') RETURNING id`, poi `INSERT INTO automobilista (id) VALUES (<id>)`.

Note sui riferimenti:

- TF-WS-03: VD_1 (gerarchia `{complete, disjoint}`): solo un Automobilista possiede un wallet.
- TF-WS-19, 20, 27…29: `trovaSosta` e `sostaPerTargaSuStallo` servono alla verifica del pagamento (RF_OP_4, SD_OP_3 2.2, 3.1); `trovaSosta` serve anche al prolungamento e alla verifica del permesso.
- TF-WS-30, 31: le soste attive di un automobilista servono a scegliere la sosta da prolungare (RF_SOSTA_2, entry condition di `UC_SOSTA_2`).
- TF-WS-36, 37: la scadenza è raggiunta all'istante uguale all'orario di scadenza (`at(orario di scadenza)`, `sincronizzazione_eventi.md` §2).
- TF-WS-42: `terminaSosta` termina tutte le soste `Scadute` dello stallo (`sincronizzazione_eventi.md` §1) ed elimina dichiarazione e foto (NRF_LEG_2).
- TF-WS-44, 46: la sosta `Attiva` o `Scaduta` sullo stallo serve alla segnalazione ANPR (RF_ANPR_1, `SD_ANPR_1` 2.1 `sostaInCorso()`); la priorità della sosta `ATTIVA` e, tra le scadute, della scadenza più recente (TF-WS-45) è del piano approvato di OMP-45, perché sullo stesso stallo possono esserci più soste non terminate (`cp_inserimento_sosta.md` §6).
- TF-WS-47…49: le soste in corso dell'Automobilista (`ATTIVA` e `SCADUTA`, dalla più recente) sono la scelta D2 del piano approvato di OMP-45 (`np_01_automobilista`, «Sosta in corso»).
- TF-WS-53, 54: la lettura con blocco della riga serve al prolungamento (RF_SOSTA_2, `SD_SOSTA_2` 2.1): due prolungamenti della stessa sosta si eseguono uno dopo l'altro. Il blocco in sé lo verifica `cp_prolungamento.md` TF-PRO-14.
- TF-WS-60, 61 (OMP-63): la verifica del permesso (RF_OP_5, `SD_OP_5` 2.1–2.3) legge la sosta con tipo di stallo ed ente e la tiene bloccata fino alla registrazione dell'esito, così due verifiche della stessa sosta si eseguono una dopo l'altra (`cp_verificaPermesso.md` VP-12). Come per TF-WS-53, il blocco in sé lo verifica il frame di concorrenza del servizio.
- TF-WS-55…59: la scadenza scatta solo se l'orario di scadenza è raggiunto all'istante indicato (`at(orario di scadenza)`, `sincronizzazione_eventi.md` §2), così l'allineamento non fa scadere una sosta prolungata dopo la lettura delle soste da scadere (`cp_prolungamento.md` TF-PRO-15). TF-WS-57: all'istante uguale all'orario di scadenza la sosta scade, come in TF-WS-36. TF-WS-58, 59: solo le soste `ATTIVA` scadono (`SCD_2`), come TF-WS-40, 41 per `impostaSostaScaduta`. Dalla OMP-61 `impostaSostaScaduta` (TF-WS-39…41, invariati) resta senza condizione sull'orario ed è usata solo per preparare i dati nei test.
- TF-WS-50…52: le soste in corso di una targa, su qualsiasi stallo, servono al riscontro ANPR per riconoscere la sosta attiva della targa letta su un altro stallo e la sua sosta scaduta sullo stallo letto (piano approvato di OMP-46, `cp_riscontroAnpr.md`).
