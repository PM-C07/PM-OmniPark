# cp_apiAmministrazione

Specifica dei casi di test (category partition) del gruppo di API dell'Amministrazione: `GET /api/admin/enti`, `GET /api/admin/enti/<id>/riepilogo`, `GET` e `POST /api/admin/ausiliari`, `PUT /api/admin/ausiliari/<id>` e `POST /api/admin/ausiliari/<id>/disattivazione`.
Requisiti: RF_ADM_1 (panoramica degli enti), RF_ADM_2 (gestione degli account degli Ausiliari), RF_AUTH_4 (accesso negato all'account disattivato), NRF_SIC_1 (solo l'Amministratore). Task OMP-62 (issue #39).

- **Fonti dell'esito atteso:** `UC_ADM_1`, `UC_ADM_2`, `SD_ADM_1`, `SD_ADM_2`, `UC_AUTH_4` 2.a2, catalogo delle operazioni di `cp_verificaAutorizzazione.md` (UC_ADM_1 e UC_ADM_2: solo Amministratore, nessun controllo di ente), TCS dei servizi (`cp_panoramicaEnti.md`, `cp_gestioneAusiliari.md`), convenzioni delle API di `cp_apiAccesso.md` §2 (formato degli errori, tabella comune codice → status), issue #39, piano approvato di OMP-62 (punto 6, decisione D3).
- **File di test:** `src/app/api/admin/amministrazione.db.test.ts`, eseguito con `npx vitest run --config vitest.db.config.ts <file>`.

## 1. Tracciabilità

Ogni frame riporta un solo riferimento, scelto in quest'ordine: un requisito dell'Elenco (`RF_…`, `NRF_…`) se il suo testo copre davvero il comportamento; altrimenti il vincolo di dominio `VD_<n>`; altrimenti `ISSUE_39` per le scelte dell'issue #39 e del piano approvato (percorsi, corpi, status).

Nome del test: `<riferimento> · <frame> · <descrizione> → <esito>`, per esempio `NRF_SIC_1 · TF-API-ADM-03 · enti chiesti da un Ausiliario → 403 RUOLO_NON_AMMESSO`.

## 2. Route verificate

Gli handler si chiamano direttamente con una `Request` reale, come negli altri gruppi di API; quelle con parametri ricevono `{ params: Promise<{ id: string }> }`.

| Metodo e percorso                               | Corpo                                      | Operazione | Facade                                          | Risposta positiva                                                                   |
| :---------------------------------------------- | :----------------------------------------- | :--------- | :---------------------------------------------- | :---------------------------------------------------------------------------------- |
| `GET /api/admin/enti`                           | —                                          | UC_ADM_1   | Amministrazione `enti()`                        | 200 `{ enti: [{ id, nome }] }`, per nome                                            |
| `GET /api/admin/enti/<id>/riepilogo`            | —                                          | UC_ADM_1   | Amministrazione `riepilogo(id)`                 | 200 `{ ente, stalliGestiti, sosteAttive, segnalazioniAperte }`                      |
| `GET /api/admin/ausiliari`                      | —                                          | UC_ADM_2   | Utenti e accessi `ausiliariPerEnte()`           | 200 `{ ausiliari: [{ id, email, nome, cognome, enteId, ente, statoDellAccount }] }` |
| `POST /api/admin/ausiliari`                     | `{ nome, cognome, email, password, ente }` | UC_ADM_2   | Utenti e accessi `creaAusiliario(utente, dati)` | 201 `{ ausiliario }`                                                                |
| `PUT /api/admin/ausiliari/<id>`                 | `{ nome, cognome, email, ente }`           | UC_ADM_2   | Utenti e accessi `aggiornaAusiliario(id, dati)` | 200 `{ ausiliario }`                                                                |
| `POST /api/admin/ausiliari/<id>/disattivazione` | —                                          | UC_ADM_2   | Utenti e accessi `disattivaAusiliario(id)`      | 200 `{ ausiliario }`                                                                |

- **Sessione:** ogni route chiama `richiediSessione(richiesta, operazione, null)`: senza cookie o con una sessione non valida 401 `SESSIONE_NON_VALIDA`; con un ruolo diverso dall'Amministratore 403 `RUOLO_NON_AMMESSO`. La sessione si controlla prima di leggere corpo e parametri. L'Amministratore che crea l'account è quello della sessione («gestisce l'account di»).
- **Corpo:** `nome`, `cognome`, `email` e `password` sono stringhe; `ente` un intero. Un campo assente o `null` arriva alla Facade come stringa vuota (o `ente: null`) e produce `DATI_INCOMPLETI`; un campo di tipo diverso, un corpo non JSON o un `<id>` non intero positivo producono 422 `RICHIESTA_NON_VALIDA`.
- **Status dei codici nuovi** (tabella comune): `DATI_INCOMPLETI` 422; `AUSILIARIO_INESISTENTE` 404; `ENTE_INESISTENTE` 404 (già presente, anche quando l'ente arriva nel corpo); `AUSILIARIO_GIA_DISATTIVATO`, `AUSILIARIO_CON_SEGNALAZIONI_PRESE_IN_CARICO`, `CAMBIO_ENTE_NON_CONSENTITO` 409. Gli altri codici restano quelli di `cp_apiAccesso.md` §2.
- **Errori:** corpo `{ errore: { codice, messaggio } }`, messaggio in italiano non vuoto.

## 4. Categorie e scelte

**Ruolo della sessione** (per ogni route): Amministratore · Ausiliario del Traffico [error] · Automobilista [error] · nessuna sessione [error]. Le scelte [error] si combinano con richieste altrimenti valide; ogni route ha almeno un frame di ruolo non ammesso e uno senza sessione.

**Panoramica:** ente esistente · inesistente [error] · id non valido [error].

**Creazione:** corpo valido · email già registrata [error] · email non valida [error] · password troppo corta [error] · ente inesistente [error] · dato obbligatorio assente [error] · corpo non JSON [error] · `ente` non intero [error].

**Modifica:** Ausiliario esistente · inesistente [error] · id non valido [error]; email di un altro utente [error]; cambio di ente con prese in carico [error].

**Disattivazione:** Ausiliario attivo senza prese in carico · con prese in carico [error] · già disattivato [error] · inesistente [error]; effetti: sessione dell'Ausiliario non più valida, accesso negato con `ACCOUNT_DISATTIVATO`.
